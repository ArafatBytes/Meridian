## What this proves

**Demo beat 6.** Photograph a scene in the report flow. In about three seconds the card says
**what is visible** — a plain sentence, all seven cues, how many people — and then **proposes**
a category you confirm or override. The photo is stored and shows up on the report afterwards.

What a judge should take away, and what to say if they ask:

- **The model never names a crime.** It answers five questions about physical cues. Our own
  code ([`app/vision/mapping.py`](../../backend/app/vision/mapping.py)) maps cues to a
  candidate category. **You** confirm it. The filed category is always a human's.
- **A photo cannot establish intent, consent, or who started something** — which is why the
  reporter confirms. Only **fraud** has no visual form at all; the other seven categories can
  be *proposed*, never asserted. Theft and robbery came off the impossible list on 10 October,
  when a staged shoplifting photo and a staged bag-snatch showed the observation is there
  even when the category is uncertain.
- **The card names which engine answered** — *live* or *on this device*. ⚠️ **It shows
  nothing when the answer came from the rehearsal cache** (owner's decision, 10 October), so
  on a rehearsed photo the absence of a badge reads as live. `engine` is still on the API
  response and saved on the report, so the honest answer exists if a judge asks — just not
  on screen. Know which photos are in the fixture before you present.
- **`unclear` is a real answer.** Only a definite `yes` proposes anything.

## Preconditions

1. **A `GEMINI_KEY_CRIME_ONE` in `backend/.env`.** Its own key, on its own Google account:
   free quota is per project, and this is what stops D07 spending D04's ingestion budget.

   ```powershell
   docker compose up -d --force-recreate api
   ```

   `--force-recreate`, not `restart` — compose reads `.env` at **create** time, so a
   restart will not pick up a newly added key. Confirm it landed:

   ```powershell
   curl.exe -s http://localhost:8000/api/v1/ai/crime-detection/status
   ```

   `gemini` must read `"configured": true`. If it says *no key set*, the recreate did not
   happen.

2. **Ollama running natively on Windows** (not in Docker — it needs the GPU without WSL2
   passthrough), with the model pulled:

   ```powershell
   setx OLLAMA_CONTEXT_LENGTH 8192
   setx OLLAMA_KEEP_ALIVE -1
   ollama pull qwen3-vl:4b-instruct-q4_K_M
   ollama run qwen3-vl:4b-instruct-q4_K_M "warmup"
   ollama ps
   ```

   `ollama ps` must read **`100% GPU`** and `CONTEXT 8192`. If it says 83% CPU, the context
   variable did not take — the default 131072 context wants ~20 GB of KV cache and pushes
   the model onto the CPU, which costs **36s per call** instead of 9.

   Two traps that each cost a full experiment, recorded so nobody repeats them:

   | Trap | Symptom | Fix |
   |---|---|---|
   | Using the bare `qwen3-vl:4b` tag | 10.7s per call, sometimes empty output | That tag is the **thinking** build and spends its budget reasoning. `think:false`, `/no_think` and `reasoning_effort` are all accepted and silently ignored. Use `-instruct-q4_K_M` |
   | Default context | 36s per call | `OLLAMA_CONTEXT_LENGTH=8192`, set as an environment variable and not in the GUI — a GUI setting on one laptop means a fresh clone hits 36s with no clue why |

3. **The database columns and the storage bucket exist.** Both were applied on 2026-10-09
   and the Supabase project is shared, so there is nothing to do unless this is a fresh
   project:

   ```powershell
   docker exec meridian-api python scripts/migrate.py status
   ```

   `20261009120000__report_evidence_photo` reads `applied`. The bucket is `report-evidence`,
   **private**, JPEG only.

4. **Signed in on the phone**, Expo Go current, same network as the laptop. Reload the app —
   the result card is rewritten and the response shape changed completely.

   ⚠️ **If you changed networks since the last run, Metro must be started with `-c`.**
   `EXPO_PUBLIC_API_BASE_URL` is **inlined into the bundle at build time**, so a cached
   bundle keeps calling the previous address no matter how many times you restart the
   server or rescan the QR code:

   ```powershell
   cd frontend
   npx expo start -c
   ```

   The app's first log line names the address it is actually using. If that is not the IP
   `run.ps1` printed, the cache is stale — nothing else is wrong.

   ⚠️ **Sign in at least an hour before running D01–D06 as the regression pass.** D04 found
   SOS had been 401ing on any session older than an hour; a walkthrough re-run reproduces
   the steps, not the stale state.

## Steps — live

1. **Reports → add a report → add a photo.** Take or pick one. Analysis starts on its own.
2. **Watch the card appear.** It should take about **three seconds** on Wi-Fi, and the
   badge next to the title should read **live**.
3. **Read the sentence.** It must describe only what is visible. If it names a crime,
   assigns blame, or says what someone intends, that is a prompt failure — note it.
4. **Check all seven cues are listed**, including the ones that read `no`. Showing only the
   hits would make an abstention look like the analysis failed to run.
5. **With a benign photo** — a street, a room, an empty desk — the card should say **"No
   category suggested"** and the category field should stay empty. This is the single most
   important step on the page: it is the behaviour the whole design exists to produce.
6. **With a staged photo** — two people in forceful contact — expect a suggested category
   with a reason beginning *"Because …"*. Change it to something else to prove you can.
7. **Type a description first, then add a photo.** The typed description must **not** be
   overwritten, and if what you wrote matches the photo the card adds *"Matches what you
   wrote"*.
8. **Submit.** Then open the report from the list: the **evidence photo** is there, with
   the sentence and the engine under it.
9. **Kill the laptop's *internet*, not the LAN**, and analyse a **new** photo. The badge
   changes to **on this device** and it takes about **9 seconds**.

   ⚠️ **Do not turn the Wi-Fi off.** The phone reaches the backend *over* that network:

   ```
   phone ──LAN, must stay up──> laptop:8000 ──internet, kill this──> Gemini
   ```

   Dropping the Wi-Fi takes out the LAN too, the request never arrives, and the app shows
   *"Network error"* — which looks like a D07 failure and is not one. Unplug the router's
   WAN cable instead, or disable internet in the router admin, keeping the Wi-Fi radio on.

   ⚠️ Have the sentence ready: *"that one ran entirely on this laptop with the network off —
   it is the slow path on purpose."* Nine seconds of silence on stage reads as a crash.
10. **Analyse one of the rehearsed photos with the network still off.** It returns in well
    under a second, and **no badge is shown** — see the note above. Confirm the answer
    matches what was captured.

## Steps — the measurement

```powershell
docker exec meridian-api python scripts/eval_crime_vision.py
docker exec meridian-api python scripts/eval_crime_vision.py --compare
```

Read the **false-accusation rate**. That is the number to quote when a judge asks *"what if
your AI is wrong about a crime?"* It is **0%** across the current set.

⚠️ **Re-run before believing a regression.** Five consecutive runs on 10 October scored
100% detection four times and 75% once — one image flipped on identical bytes at
`temperature: 0`. Zero temperature constrains sampling, not the serving stack. A one-image
move on a six-image set is within variance, and it is the measured argument for the replay
tier: a photo that reads `assault` in rehearsal can read `nothing` on stage.

⚠️ **The harness will warn you if every image is benign**, which it currently does. With
only negatives the numbers measure **abstention**, not detection, and nothing yet shows that
either model *recognises* a real confrontation. 30–40 images with positives is the gate —
see DEMO_PLAN §9.3. The harness runs with the replay tier excluded so a rehearsed photo can
never answer its own exam.

## Capturing the rehearsed photos

Put the staged demo photos in [`backend/data/demo/vision/`](../../backend/data/demo/vision/),
then:

```powershell
docker exec meridian-api python -m app.agents export-vision-replay
```

**Run this after the final rehearsal, not before.** It freezes whatever the models say at
that moment, so an early capture preserves an answer nobody has signed off on.

Why a cache is a tier at all, given two working models: **it is the only one that guarantees
its output.** Google can change what sits behind `gemini-3.5-flash-lite` between rehearsal
and the 24th, and temperature 0 constrains sampling, not the model version.

## Fallbacks

The chain covers every failure, which is the argument for three tiers:

| On the day | Serves | Outcome |
|---|---|---|
| Everything works | Gemini | ✅ ~2s, live |
| Wi-Fi dies, rehearsed photo | **Replay** | ✅ Instant, and the verified answer |
| Wi-Fi dies, judge's new photo | Local | ⚠️ Works, **~9s.** Narrate it |
| Gemini refuses a staged violent photo | Replay, then local | ✅ Neither has a filter |
| Gemini quota exhausted or 500 | Replay / local | ✅ |
| Gemini silently changed behaviour | **Replay** | ✅ The only tier that catches this |
| All three unavailable | — | Honest "could not analyse"; **photo still stored** |

## Rough edges

- **The eval set is six images.** Four positives were added on 10 October and all four are
  detected with the correct category, which is the first evidence this pipeline detects
  anything. But they are **staged stock photos**, not real Bangladesh street scenes, and six
  is a small set. ⚠️ They are **watermarked previews and not licensed** — fine for an internal
  eval set, not for anything published or shown in a deck.
- **The local tier is markedly weaker than cloud.** On the same four positives: cloud 4 of 4,
  local 3 of 4. It also mislabelled one outdoor scene as indoor and read a bag strap as
  *"possibly a weapon"*. It is the offline fallback, not an equal.
- **Gemini's safety filter cannot be disabled** through the OpenAI-compatible endpoint —
  `safety_settings` is rejected in both documented forms — so the cloud tier **may refuse**
  a staged violent photo. Unmeasured. Run the three staged photos through it a week out;
  it is a five-minute test. The local tier has no filter, which is why the chain is the
  mitigation rather than a fourth provider.
- **If the venue Wi-Fi dies, the phone cannot reach the laptop either** — and then no tier
  helps, because the request never leaves the phone. The three-tier chain covers Gemini being
  unreachable; it does nothing about the backend being unreachable. Run the **laptop's Mobile
  Hotspot** and put the phone on it, so the LAN lives inside your own two devices and venue
  Wi-Fi only ever supplies internet, which the chain already handles losing.
- **A photo is uploaded at analysis time**, so abandoning the report leaves an orphaned
  object in the bucket. Harmless at demo volume (JPEG only, 10 MB cap); not cleaned up.
- **The image still contains the deleted ML packages** until `docker compose build api`.
  Nothing imports them; the rebuild is what reclaims the gigabytes.
- `prepare()` can make a *small* image slightly larger, because re-encoding is what strips
  EXIF and it always runs. Real phone photos shrink a lot. Correct as it stands — the
  privacy step is not optional.
