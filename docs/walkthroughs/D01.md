# D01 — Risk flags on the map, and an SOS that leaves a record

**Ran on:** iPhone, Expo Go · **By:** Nakib · **Date:** 2026-10-07 · **Takes:** ~12 minutes

**Every step below passed on a real device.** Two bugs were found by running it that no test caught,
and both are fixed: the map rendered as a blank white page on iOS, and one SOS froze the whole API for
2 minutes 34 seconds. See *Rough edges* and *Fallback* for what is still imperfect.

## What this proves

Two of the nine demo beats, at their thinnest:

- **Beat 1** — the map shows a live risk surface: flags across Dhaka, coloured by severity, with the
  expired ones already gone. Not a populated table. Pins you can see.
- **Beat 9, first half** — an SOS is delivered *and leaves a row behind*. Until D01 the alert vanished:
  the email went out and `sos_incidents` held zero rows, so there was nothing to show afterwards.

A judge watching this concludes: there is a real geospatial risk layer, it decays on its own, and the
emergency path is auditable. Nothing here yet proves the data is *live* — that is D04.

## Preconditions

- [ ] **The two SQL files have been applied to Supabase.** See *Applying the schema* below. This is
      the one step that needs the dashboard.
- [ ] `backend\venv` exists — `backend\venv\Scripts\python.exe --version` prints 3.12.x
- [ ] `.\scripts\run.ps1` is up and `http://<your-LAN-IP>:8000/health` returns 200
- [ ] `cd frontend; npx expo start --clear` is running and the phone is on the **same Wi-Fi**
- [ ] On iOS the map is **Apple Maps** and needs no API key. If the map area is blank white, the
      provider has been forced back to `PROVIDER_GOOGLE` somewhere — see *Rough edges*
- [ ] Signed in to the app with an account that has **at least one emergency contact with an email
      address** — without one, SOS returns 400 and step 9 cannot run
- [ ] `backend\.env` has `SMTP_USER`, `SMTP_PASSWORD` and `FROM_EMAIL` filled in, or no email is sent
      and step 9 only proves half of itself

### Applying the schema

`psql` is **not installed on this machine**, so `.\scripts\seed.sh` on its own cannot apply anything —
it detects the missing tool and prints these instructions instead. Use the `--sql` path; it needs only
Python:

```powershell
.\scripts\seed.sh --sql
```

writes four numbered files to `.seed-sql\`. **You only need two of them.** `1-schema.sql` is the
baseline and is already applied to this project (S01 verified it live); `4-verify.sql` checks that
baseline and knows nothing about D01's tables.

In the Supabase dashboard → **SQL Editor**, run, in order:

| File | What it does |
|---|---|
| `.seed-sql\2-migrations.sql` | Creates `risk_flags`, `raw_documents`, `extracted_incidents`, `agent_runs`, `schema_migrations` |
| `.seed-sql\3-fixtures.sql` | Loads 22 sample Dhaka risk flags |

Both are safe to run twice. The last statement of `3-fixtures.sql` prints its own result, and **it
should read `22 | 20 | 2`** — twenty-two seeded, twenty live, two already expired.

Regenerate `3-fixtures.sql` rather than reusing an old copy: its timestamps are relative to when it
was generated, so yesterday's file seeds a map of expired flags.

## Rough edges

Specific, and each one says whether it is scheduled.

- **The pins are plain `react-native-maps` markers.** No custom icon, no severity number on the pin
  itself, no distinction between confirmed and unconfirmed except in the callout text. **Scheduled:**
  D02 adds the detail sheet, D05 makes confirmed and unconfirmed visually different on the map.
- **Flags do not reload when you pan.** The map is driven by a controlled `region` prop and a
  region-change handler risks the map fighting the user's finger, so D01 fetches once per recentre
  over a generous ~39 km box instead. Pan far enough out of Dhaka and the layer goes stale without
  saying so. **Scheduled:** D04 adds pull-to-refresh and a "last updated" indicator.
- **All the data is sample data.** Every source reads `sample_prothom_alo`, `sample_the_daily_star` and
  so on, with `sample:` URLs that do not resolve. That is deliberate — fabricated links that looked
  real would be worse. **Scheduled:** D04 replaces these with genuine articles from live ingestion.
  **If you are on stage on the 24th and the flags still say `sample_`, say so out loud.**
- **The SOS video is not retained.** The clip is attached to the email and then deleted. Keeping it
  would need a storage bucket, a retention window and an access policy for footage recorded under
  duress, none of which exists. The incident row records *that* a video was attached. **Not currently
  scheduled** — raise it if the demo needs it.
- **Evidence video is 640×480 at 1.2 Mbps**, about 2 MB for 10 seconds. Deliberate: at default iPhone
  quality the same clip was 16.45 MB and took 2m34s to email. It is legible as evidence, and it is not
  going to win any awards. **Not scheduled** — if higher quality is ever wanted, the email path has to
  stop being the transport first.
- **The progress bar is partly simulated.** `HomeScreen` runs a timer-driven bar capped at 98% so the
  UI moves even on a fast local network. Real upload progress overrides it when available. The stage
  label is honest about which phase you are in; the percentage is indicative.
- **`as_of` changes *which* flags are served but not their severity numbers.** Step 8b shows flags
  dropping out as the instant advances, which works. What does not work yet is a flag visibly *fading*
  first: `severity_0` is always the severity at observation. **Scheduled:** D02 computes severity on
  read and adds the on-screen time control, so the fade is watchable rather than inferred.
- **The time control is curl-only.** There is no UI for `as_of` — the app always asks for now.
  **Scheduled:** D02 (dev-only control), D09 (a real forward-looking one).
- **iOS shows Apple Maps, Android shows Google Maps.** The two look different — different tiles,
  different labels, different marker styling. That is a deliberate consequence of not having a Google
  Maps API key: Google Maps on iOS needs a paid key *and* a development build instead of Expo Go.
  Decide before the 24th which device you are demoing on and rehearse on that one. **Not scheduled**;
  it is a cost-and-credentials decision, not an engineering one.
- **Nothing has written to `user_locations` yet**, so `endpoints/tracking.py` is still unexercised.
  It uses the same geoalchemy2 geography path that was broken until D01 set `search_path` on the
  engine, so it is *probably* fixed now too — but "probably" is the honest word. **Not scheduled**;
  worth a minute whenever someone touches tracking.
- **The backend will not start without the full AI stack** (~2 GB: torch, mediapipe, ultralytics),
  because `api/v1/api.py` imports the vision endpoints eagerly even though D01 touches none of them.
  **Scheduled:** Track B (B3), endpoint auto-discovery.
- **`./scripts/check.sh` reports ~320 ruff findings in pre-existing code.** They are real but they are
  not D01's: ruff had never actually run on this repository, because with no venv `check.sh` skipped
  the step and the skip read as a pass. D01's own files are clean and D01 added zero new findings.
  **Partly scheduled:** Track B (B3, B5).

## Fallback if it fails live

| If this fails | Do this |
|---|---|
| The phone cannot reach the backend (step 5 shows red) | Check `EXPO_PUBLIC_API_BASE_URL` is the LAN IP. `.\scripts\run.ps1` sets it automatically; a stale value in `frontend\.env` overrides it. Last resort: show step 1's curl output on the laptop — the data is the point, the pill is not. |
| The map area is blank white on iOS | This was a real bug, fixed in D01 — `provider={PROVIDER_GOOGLE}` forced a Google Maps SDK that Expo Go for iOS does not contain, so `MapView` rendered an empty rectangle with no error. The provider is now `MAP_PROVIDER` (Apple Maps on iOS, Google on Android). If it recurs, check `src/components/MapComponent.tsx` and press `r` in the Expo terminal to reload. |
| The map area is blank on Android | Expo Go supplies its own Google Maps key; a development build needs a real one in `app.json`, which this project does not have. Show the iPhone instead. |
| `risk_flags` is empty | Re-run `.\scripts\seed.sh --sql` and paste `3-fixtures.sql` again. Regenerate it — do not reuse an old file, or every flag seeds already-expired. |
| SOS does not deliver an email | Step 13 still works. Show the row and say the alert was recorded and the SMTP credential is the failure. Honest, and it demonstrates exactly why the audit trail was worth building. |
| The SOS takes more than ~20 seconds | Check the clip size in the backend log (`.\scripts\run.ps1 -Logs`, look for "Video saved"). If it reports double-digit MB, the bitrate caps in `SOSCameraModal` are not being honoured on that device — fall back to describing the flow and show a previously delivered email. |
| Supabase is unreachable entirely | There is no offline path in D01. `RISK_SURFACE_IMPL=seeded` is **D02**, and the recorded fallback video is D10. If this is a risk for your rehearsal, that is an argument for D02 landing on time. |
