# D02 — The surface breathes

**Ran on:** iPhone, Expo Go · **By:** Nakib · **Date:** 2026-10-07 · **Takes:** ~10 minutes

**Every step below passed on a real device.** Run two days ahead of D02's scheduled dates (Oct 9–10),
which is the first slack this plan has had.

Two things were found while getting to the device rather than on it, and both are fixed: the seeder
crashed when run from the repository root, and `.\scripts\seed.sh` turned out not to run in PowerShell
at all — it returns silently and changes nothing, so a stale 22-flag fixture file looked like a
successful regeneration. See *Rough edges*.

## What this proves

Demo beats 2 and 5, and it is the sprint that makes the whole demo survive a bad network.

- **Beat 2** — tap a flag and the surface explains itself: what kind of thing it is, how severe it
  was when observed, how severe it is **now**, its half-life, how long until it leaves the map, how
  many sources agree.
- **Beat 5** — move the map's clock forward and watch flags **fade and then disappear on their own**.
  No stale red zones, and no cron job deciding when: severity is computed on read.
- **~200 flags across Dhaka**, so beat 1 looks like a city rather than a handful of pins — and they
  work with the database stopped, which is what D10's failure drills rehearse.

A judge watching this concludes: the risk layer is time-aware rather than a static heatmap, it
retires its own claims, and every number on screen has a stated provenance. What it does **not** yet
prove is that the data is live — every source says `sample_`, and live ingestion is D04.

## Loading the flags

**This has to be done before step 1, and it is the only step that needs the Supabase dashboard.**

**In PowerShell, run the Python directly:**

```powershell
cd D:\Study\Competitions\Meridian
.\backend\venv\Scripts\python.exe backend\scripts\seed_risk_flags.py --sql --out .seed-sql\3-fixtures.sql
```

**Not `.\scripts\seed.sh --sql`.** PowerShell cannot execute a `.sh` file: it returns immediately,
prints nothing, and changes nothing, so it looks like it worked. That cost real time once already. If
you want the shell script — it also refreshes `1-schema.sql`, `2-migrations.sql` and `4-verify.sql` —
run it from Git Bash, or as `bash scripts/seed.sh --sql`. For D02 only `3-fixtures.sql` has changed,
and the command above is the whole job.

Then paste **`3-fixtures.sql`** into the Supabase SQL Editor and run it. It clears every row whose `event_key` starts `seed-` and inserts 212 fresh ones, so
re-running it is safe and is the right move if a rehearsal has been going for hours.

**Regenerate it rather than reusing an old copy.** Every observation time in that file is relative to
the moment it was generated, so a file from yesterday seeds a map of expired flags — which is
precisely the failure that looks like a broken product.

The last statement in the file reports what landed:

```
 seeded | live_now | already_expired
--------+----------+-----------------
    212 |      ~19x |              ~1x
```

`already_expired` is not a problem. Six fixture entries are deliberately below the serve threshold so
that the expiry filter is visible in step 4 rather than taken on trust, and two of the eight chronic
units (Barishal, Rangpur) have a `normalized_risk` below 5.0, which means they expire the instant they
are created. Both are correct.

## Switching the surface (steps 14–17)

**There is no database container to stop.** The database is Supabase, and it is remote —
`docker-compose.yml` runs only the API and Redis. So "take the database away" means pointing
`DATABASE_URL` somewhere that does not exist.

**The backend is a Docker container called `meridian-api`.** Code changes hot-reload through a bind
mount, but **`.env` changes do not**: the file is read by Compose when the container is *created*, so
`docker compose restart api` keeps the old values. Recreate it instead:

```powershell
# after editing backend\.env
docker compose up -d --force-recreate api
```

One command — no separate stop. It takes 20–40 seconds to come back, because importing torch,
mediapipe and cv2 is slow. Watch it with `docker compose logs -f api`, or just wait for
`http://localhost:8000/health` to answer 200.

Other useful forms: `.\scripts\run.ps1 -Down` stops everything, `docker compose stop api` stops just
the API, `.\scripts\run.ps1 -Logs` tails the log.

**Expo does not need restarting** — it runs on the host and is unaffected. But the map does not poll,
and **there is no pull-to-refresh until D04**, so after recreating the container you have to make it
refetch. The easiest way is the control you are already testing: **tap `+3h`, then `now`.** Both tap
the endpoint. Pressing `r` in the Expo terminal reloads the whole app and also works.

**For step 15**, in `backend\.env`, change the host in `DATABASE_URL` to something that cannot
resolve — append `-dead` to it — then `docker compose up -d --force-recreate api`. The map must still
show ~190 flags while anything database-backed fails. Put the real value back for step 17.

> This was verified in Python before the walkthrough was written, and
> `tests/invariants/test_surfaces_agree.py::test_the_seeded_surface_serves_with_no_reachable_database`
> now pins it: **191 flags served against a `DATABASE_URL` pointing at a non-existent host.** It works
> because SQLAlchemy connects lazily and the seeded surface never runs a statement — the endpoint still
> takes a session, it just never uses it. Worth knowing that the guarantee is that narrow: anything
> that made `get_db` connect eagerly would break the offline path while leaving it looking fine.

## Rough edges

- **`.\scripts\seed.sh` does not run in PowerShell, and it fails silently.** PowerShell cannot execute
  a `.sh`: the command returns at once, prints nothing and changes nothing, which reads exactly like
  success — leaving the previous sprint's 22-flag `3-fixtures.sql` in place. Every `.sh` in `scripts/`
  has this problem; only `run.ps1` is native. *Switching the surface* and *Loading the flags* above
  both give PowerShell-native commands now.
- **`.env` changes need `--force-recreate`, not `restart`.** Compose reads `backend\.env` when the
  container is created, so `docker compose restart api` silently keeps the old values. This is the
  trap behind steps 14–17 and it is written out in *Switching the surface*.

- **The "as of" control is six preset buttons, not a slider.** A slider needs a dependency the
  project does not have (`@react-native-community/slider` is not installed) and a dragged value fires
  a request per frame. Presets are also more repeatable on stage. D09 promotes this to a real
  forward-looking control over the same `as_of` parameter.
- **Restarting the backend with `RISK_SURFACE_IMPL=seeded` resets every flag to fresh.** Fixture
  offsets are relative and are resolved once per process. Usually what you want before a rehearsal;
  worth knowing if you are mid-rehearsal and wondering why decay reset.
- **The chronic baseline is one flag for a 20 km police-unit area.** `scripts/crime_risk_model.json`
  is real published Bangladesh Police statistics, and it has no finer granularity than the unit. It
  is a baseline, not a blackspot map, and the honest answer in Q&A is that street-level chronic
  detection is B11's archive mining. Its circle is not drawn, deliberately — a 20 km disc over the
  viewport is a tint, not information.
- **Two of the eight chronic units expire immediately.** Barishal and Rangpur normalise below the
  serve threshold of 5.0. Correct behaviour, slightly odd to read in the seed output.
- **`severity_now` is computed in Python, not in PostGIS.** S20 asked for decay at query time in SQL.
  The time-of-day profile is a 24-element array lookup against the Dhaka-local hour, and putting that
  in SQL means duplicating `app/scoring/decay.py` in a second language in the hot path. The reasoning
  is written out in `surface_db.py::_row_to_flag`. The spatial test and the liveness filter — the
  parts that need the index — are still SQL.
- **Only one `clash` flag in 204 entries.** Not an oversight: it is the kind hardest to source
  responsibly, and the framing templates are what make it safe to display at all.
- **Flag taps do not work in route mode.** By design — the whole risk layer is hidden there.
- **`route_service._get_regional_risk()` still exists and is now a double count.** D02 moved the same
  police model into the surface. Deleting it is a D06 checkbox; the method carries a comment saying
  so. It affects route scores only, and routing is not demoed until D06.

## Fallback if it fails live

| If this fails | Do this | Say this |
|---|---|---|
| The map loads no flags at all | Check the status pill. "Risk layer unavailable" means the backend is unreachable, not that there is no data. Restart `run.ps1`. | — |
| Flags load but all one colour | Severity is not reaching the client. Switch to `RISK_SURFACE_IMPL=seeded` and restart; the fixture cannot be wrong about severity. | Nothing — this should not happen on stage. |
| The database is down or slow | **`RISK_SURFACE_IMPL=seeded`, restart the backend.** Step 15 is the rehearsal for exactly this. | "This is the seeded surface — the same code path, no database. It is how the product degrades." |
| The flags are all expired | Regenerate and re-run `3-fixtures.sql`. An old copy of that file seeds a stale map. | — |
| The "as of" control is missing | You are on a production build. Use Expo Go. | — |
| A judge asks whether this is real data | Do not hedge. | "These 204 are hand-built sample flags — every source is marked `sample_`. The chronic layer underneath is real published police statistics. Live news extraction is the next thing we built; I can show it." |
