## What this proves

**Demo beat 4.** Ask for a route and you no longer get one line and a number. You get
ranked alternatives, each coloured by how safe it is, each with **one sentence of plain
English saying what is on it and what choosing it costs** — and the flagged corridors drawn
on the map so the comparison reads without anyone narrating it.

Underneath, four things changed that a judge may well ask about:

- Routing runs on **our own OSRM graph**, not a public demo server someone else rate-limits.
- Durations are **OSRM's**, from the road network, not distance ÷ 30 km/h.
- Risk comes from the **risk surface** — one PostGIS corridor query — so the same scoring
  works on live news flags and on the offline fixture.
- There is **one score**: `safety_score`, 0–100, higher is safer. There used to be three.

## Preconditions

1. **The OSRM graph exists and the container is serving it.** This is §9 background work
   and D06 assumes it is done:

   ```powershell
   docker compose ps osrm
   curl.exe -s "http://localhost:5000/route/v1/driving/90.4074,23.7104;90.3687,23.8069?overview=false"
   ```

   The container reads `Up`, and the curl returns `"code":"Ok"`. If it restart-loops, the
   `.osrm` files are missing — rebuild per `docker-compose.yml`'s `osrm` service comment.

2. **`backend/.env` points at it:**

   ```
   OSRM_BASE_URL=http://osrm:5000
   ```

   `osrm`, not `localhost` — that hostname resolves on the compose network, where `api`
   lives. After changing it, `docker compose up -d --force-recreate api` (compose reads
   `.env` at create time, not on restart).

3. **Signed in on the phone**, Expo Go current, same Wi-Fi as the laptop. Reload the app —
   the route card is a new component and the response gained five fields.

### Honesty in the trade-off sentence

Step 8 is worth dwelling on, because the first implementation got it wrong and it read
perfectly.

Option 2 *does* avoid two flags the recommended route passes — the literal count is 2. But
it is also two minutes slower and passes five flags to the recommended route's three. Saying
*"2 minutes longer, avoids 2 flagged corridors"* would be **true and misleading**: it sells
a strictly worse route on the half of the comparison that flatters it.

So an alternative may claim "avoids N" **only when it is actually safer**. Otherwise it gets
the time difference and nothing else. The flags it passes are listed either way, so nothing
is hidden — it just is not advertised.

### The detour generator

Step 10 returns one route, and OSRM is the reason: it offers alternatives only when a
geometrically distinct road exists. Measured across five Dhaka pairs on 2026-10-09, three
returned two routes and two returned one. **A demo beat cannot depend on the audience's
origin and destination being a lucky pair.**

So when there is one candidate and it passes a live flag worth avoiding, D06 builds the
alternative itself: push a waypoint perpendicular to the route, far enough to clear the
flag's radius plus the scoring corridor, and ask OSRM to route through it.

Two things about it are deliberate:

- **Chronic flags are not detour targets.** The historical layer covers most of Dhaka with
  2 km radii, so "avoiding" one usually means avoiding the city. Live events are what you
  detour around. Step 10's route passes only chronic flags, which is why no detour appears
  there.
- **The result is verified, not trusted.** OSRM snaps a waypoint to the nearest road, and
  that is sometimes the road we were trying to leave. If the candidate still passes the flag
  it was built to avoid, it is **discarded** — offering a "safer alternative" that passes the
  same fire would be worse than offering one route.

### Why the duration was wrong, and what "from the road graph" cannot fix

`14 min` for `12.6 km` is 54.8 km/h. Measured on the graph:

```
12.61 km in 13.8 min            =>  54.8 km/h average
segment speeds (n=324)          =>  min 10, median 56, max 106 km/h
```

**OSRM is not wrong.** It is answering the only question the graph can answer: *how long on
an empty road*. `car.lua` speeds come from `maxspeed` tags and road-class defaults, and
**there is no traffic information anywhere in an OSM extract** — so no amount of rebuilding
the graph produces a Dhaka-realistic number. That is the honest answer to "can we fix this
from the road graph": not from the graph alone, no.

Three ways out, in order of correctness:

1. **`osrm-customize --segment-speed-file`** — OSRM's own mechanism for exactly this, fed
   per-segment observed speeds. The proper fix, and it needs a traffic data source this
   project does not have. **Track B.**
2. **A rebuilt profile with Dhaka-realistic speed caps** — more principled than a blanket
   multiplier, still a guess, and it costs a multi-hour graph rebuild.
3. **A congestion factor applied to OSRM's duration** — what D06 does.
   `ROUTE_CONGESTION_FACTOR = 0.35` brings that route to **39 min, ~19 km/h**.

The factor is crude but has two properties worth keeping: it preserves the *relative*
differences between roads, so a flyover segment still beats an alley and the ranking stays
meaningful; and it is one number in one place with its derivation attached. A test asserts
it cannot reorder routes, because the obvious "improvement" — varying it by road class —
would start deciding the recommendation on a number nobody has calibrated.

⚠️ **It is a calibration, not a measurement.** Scaled from one reading on one corridor.
**Check it against a journey you actually know before quoting a duration on stage.**

### The walking profile is honest, not finished

Step 12's caveat is not boilerplate. The graph is built from `car.lua`, and **OSRM will
answer a `/foot/` request from whatever graph it has** — so a walking route obeys car turn
restrictions and may use a flyover.

Measured: a `/foot/` request returned **7.03 km in 9 minutes**, identical to the driving
answer. 47 km/h presented as a walk is not an imprecision, it is a false statement on a
screen, so the duration is recomputed at 4.8 km/h and the path caveat is shown to the user
rather than buried in a log. The real fix is a second graph built with `foot.lua`; it is not
demo-critical and it is not in D06.

## Fallbacks

- **"No routes found" or a straight line across the city.** The engine is unreachable. The
  card will say so — `straight-line` produces *"No routing engine answered. This is a
  straight-line estimate, not a road route."* Check `docker compose ps osrm` and
  `OSRM_BASE_URL`.
- **A card note about a public demo server.** The local container did not answer and the
  fallback was used. Routes still work, on a stranger's rate limiter — fix before relying on
  it. This path is deliberately loud; D10's failure drills exercise it.
- **Every route shows the relaxed-preference note.** Expected if you lower
  `max_crime_score` below what any Dhaka route achieves. Nothing is broken; the app is
  telling you it could not honour the preference rather than returning nothing.
- **One route where you expected two.** Either OSRM found no distinct alternative *and* the
  route's flags are all chronic (so no detour was built), or the detour was built and
  discarded for still passing the flag. The API log says which.

## Rough edges

- **The search box asked the geocoder questions nobody had asked** (found 2026-10-16, fixed).
  The suggestion list was driven by the *contents* of the two fields, and the code writes to
  those fields too — a map tap writes `Selected Location`, a POI tap writes the place's name,
  Resume writes the stored destination label. So a tap on open ground in Dhanmondi produced a
  suggestion for *"A location selected by Seoul for its scenic views, Jeungsan-ro 17-gil,
  Eunpyeong-gu, Seoul"*. Nothing was wrong with the geocode: Nominatim was handed the words
  "Selected Location" and returned the closest thing in the world to them. The rule is now
  about **provenance** (`features/search/suggest.ts`): only a keystroke is a search. Blocking
  the string itself would have fixed the screenshot and left the POI tap — searching
  "Star Kabab" and offering a different Star Kabab across the city — in place. Worth
  remembering for the cache numbers in §Verified: those unasked questions were also
  **spending the Nominatim budget**, one request per map tap.
- **The chronic layer had to be down-weighted, and that was the finding of the sprint.**
  Scored at full weight, a 12.6 km Dhaka crossing passing three chronic flags scored
  **16.7/100**; every route in the city scored about the same; `max_crime_score` therefore
  rejected all of them, so defect 6's filter was meaningless and the ranking reflected
  historical coverage rather than today's events. That is precisely the **"stale red zones"**
  failure demo beat 5 exists to disclaim, and concept document §9's commitment not to label
  areas permanently. `ROUTE_CHRONIC_WEIGHT=0.35` brings the same route to **68.6** and lets a
  live event move the number. **Raise it only with a measurement.**
- **Walking paths come from the car graph.** Durations are corrected and the caveat is on
  screen; the geometry is not fixed. A second `foot.lua` graph is the answer.
- **`ROUTE_CONGESTION_FACTOR = 0.35` is calibrated from one measurement on one corridor.**
  It decides what the app tells someone about their journey, and nobody has checked it
  against a real trip. The proper fix is a segment-speed file — Track B.
- **`ROUTE_CORRIDOR_RADIUS_M` is 150 m and is a judgement, not a measurement.** Wide enough
  that a flag beside the carriageway counts, narrow enough that one on a parallel street two
  blocks over does not. Nobody has checked it against real road geometry.
- **The detour generator fires only on live flags above severity 20.** A route whose flags
  are all chronic or nearly expired gets one route, by design — but it means beat 4's
  "alternatives" are not guaranteed for an arbitrary pair. Use the Dhanmondi→Gulshan pair on
  stage, where OSRM supplies them.
- **`/routes/safest` returns `routes[0]`** and is therefore the composite winner, not the
  highest `safety_score`. The name predates the composite. Not renamed because it is a
  public endpoint; worth knowing before quoting it.
- **The ranking test exists, but it is not end-to-end through OSRM.**
  `test_the_top_route_avoids_a_flagged_corridor` covers S12's last bullet — two corridors,
  one flag, ranked by the real composite — and its twin asserts the other direction, that a
  trivial flag does not justify a long detour. Neither goes through OSRM or a database, so a
  regression in *route generation* rather than in ranking would still need the device run to
  catch. That is the gap §0 exists to cover.
