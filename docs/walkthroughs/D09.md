# D09 — tomorrow's map, and the loop closed

**Ran on:** Expo Go, Android · **By:** Nakib · **Date:** 2026-10-10 — **all steps passed**

**Plan:** `DEMO_PLAN.md` §D09 · **Beats:** 8 (tomorrow's map) and 9's second half (the record)

> **The sentence this sprint defends:** *an announced procession is on the map before it happens,
> and it is not on the map before it is due.* Both halves matter. Step 2 is the first; step 3 is the
> second, and it is the one a competitor would get wrong.

---

## Before you start

1. **No migration.** D09 adds no columns and changes no contract. `valid_from` and `valid_to` have
   been on `risk_flags` since D01, and `sos_incidents` already holds everything the history screen
   reads. If you were expecting to run SQL for this sprint, see the withdrawn item in
   `DEMO_PLAN.md` §D09 — the SOS foreign key points at the `public.users` mirror, but the *value*
   stored is the auth user id, so nothing needed moving.
2. API and app running: `scripts/run.ps1` (or `run.sh`). If the LAN IP changed, the app needs
   `npx expo start -c` — `EXPO_PUBLIC_*` is baked into the bundle.
3. **The three forward-dated flags have to be in whichever surface is serving.** They are fixture
   entries (`seed-scheduled-*`); live announcements are step 7 and are not required for the beat.
   `RISK_SURFACE_IMPL` is **unset in `backend/.env`, so the `config.py` default `db` applies** —
   which means the fixture reaches the map only once it has been loaded into the table:

   ```
   cd backend
   python scripts/seed_risk_flags.py
   ```

   It clears `seed-%` and re-inserts, and **never touches a flag an agent produced** (`live-`,
   `sched-`). Expect `215 flag(s)`. This is the path worth testing, because it exercises the real
   SQL predicate — including D09's `valid_from` floor — rather than the Python mirror.

   The alternative is `RISK_SURFACE_IMPL=seeded`, which reads the fixture from disk instead. If you
   use it, **restart the API**: that surface loads the fixture once per process and anchors every
   relative time to that instant, so an API started before these entries existed serves the old set
   and shows nothing at Tomorrow.
4. One emergency contact saved, for step 5. Profile → Emergency Contacts.

Check the surface before you touch the phone. Ask it about now, then about tomorrow:

```
curl "http://127.0.0.1:8000/api/v1/risk/flags?bbox=90.33,23.70,90.50,23.90"
curl "http://127.0.0.1:8000/api/v1/risk/flags?bbox=90.33,23.70,90.50,23.90&as_of=<tomorrow>Z"
```

- [ ] The first response contains **no** `event_key` starting `seed-scheduled-`.
- [ ] The second contains **three** of them, each with a non-null `valid_from` and `valid_to`.

That difference is the whole sprint, visible before any UI is involved.

This is the half that is easy to get wrong. A scheduled flag served from the moment it is written
would sit on tonight's map at full severity — nothing has decayed yet — and would bend tonight's
routes around a road that is currently clear.

## Known limits, stated rather than discovered on stage

- **Beat 8 runs on the fixture.** The three forward-dated flags are seeded. The agent that writes
  real ones is built, registered on an hourly cron and verified end to end, but live Bangla
  announcements that state an hour are rare enough that a given run usually publishes nothing. If
  asked: the agent is real, the surface is seeded, and `RISK_SURFACE_IMPL` is the switch.
- **Live news ingestion is thin, and it is not a D09 regression.** Measured 10 Oct: 24 documents
  stored in total, 4 extracted incidents, **1 flag ever published and it has expired**, and three
  of those four incidents failed to geolocate. The relevance filter passes about 1% of listed
  articles and the ones it passes are already stored, so recent `live_risk` runs read `in=0 out=0`.
  Beats 1 and 2 therefore run on the seeded surface too. Raised as its own decision; widening the
  sources is B11a.
- **The news page is almost entirely sample data, and says so.** 0 real articles of 25 on 10 Oct
  (1 of 26 on the seeded surface). It was
  built anyway, as the surface on which next phase's ingestion work will be visible, which is why
  the "real of" counter and the `Sample data` tags are prominent rather than tactful.
- **Two announcements of one procession make two pins.** Cross-article corroboration of scheduled
  events is deliberately not wired to Rumour Guard: it matches on observed time, and two papers can
  carry the same call a day apart, so running it risks merging two different events into one
  `confirmed` claim. A duplicate pin is cosmetic; a false confirmation is not.
- **`end_hour` is trusted only when it is after `start_hour`.** `22:00–02:00` and a misread
  `14:00–14:00` are indistinguishable from one integer, so both fall back to the per-kind default
  duration. A window wrong by hours beats one wrong by a day.
- **The shake threshold is still 6.0 g** while the comment above it says 3.5. Carried over
  unchanged from `HomeScreen` rather than reconciled, because changing a trigger threshold inside a
  refactor means two changes with only one of them tested. B5 owns it.
