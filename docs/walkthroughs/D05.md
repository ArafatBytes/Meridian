# D05 — Verification you can see

**Ran on:** Expo Go · **By:** Arafat · **Date:** 2026-10-08 · **Takes:** ~8 minutes

**All 11 steps passed on a real device, first run, no issues found** — including the
promotion (steps 7–9) and the reset (step 11). Unusually for this project, running it on
a phone found nothing that the backend verification had not already found; the three
defects D04 turned up came from exactly this kind of run, so a clean pass is worth
stating rather than assuming.

## What this proves

Demo beat 2, and the half of beat 1 that D04 could not reach. The map no longer treats
every claim as equal: a flag reported by **one** outlet is drawn **hollow and dashed**
with a `?` on it, a flag **two independent publishers** agree on is drawn **solid** with
the source count on it. Tap either and the sheet tells you which publishers, when we
decided to believe it, and — for an unconfirmed one — that it is counted at **60%
weight rather than hidden**.

Then you run one command and **watch a flag promote itself** while the map is open.

What a judge should notice: *we publish the unverified claim and label it* rather than
either suppressing it or pretending it is corroborated. The concept document commits to
exactly that, and the database will not store a violation of it.

## Preconditions

1. **The D05 migration is applied** (`20261008140000__risk_flags_confirmed_at`):

   ```powershell
   docker exec -w /app meridian-api python scripts/migrate.py status
   ```

   All four must read `applied`. `migrate.py up` applies the new one.

2. **The embedding model is present.** It downloads once (~90 MB) into the model
   cache volume on first use:

   ```powershell
   docker exec -w /app meridian-api python -c "from app.agents.rumour_guard import embeddings_available; print(embeddings_available())"
   ```

   `True`. A `False` here is **not** fatal — deduplication switches off and every
   incident becomes its own unconfirmed flag, which is the pre-D05 behaviour — but
   steps 7–9 need it.

3. **At least one unconfirmed flag is on the map**, which is all but guaranteed: the
   D02 fixture carries ~39 of them.

4. **Signed in on the phone**, Expo Go current, same Wi-Fi as the laptop. Reload the
   app after pulling — the marker is a new component and the contract gained two
   fields.

### Saying this honestly on stage

Step 8 injects a second source. **Say so**, and say why:

> *"I'm injecting the second source here so you can watch the transition on demand.
> The code that decides to promote it is the same code that runs against live news —
> what I can't schedule is a second newspaper publishing in the next ninety seconds."*

That is not a hedge, it is the stronger claim: the promotion goes through
`rumour_guard.merge_into()`, the same function live ingestion calls, with the same
independence rules and the same database constraints. Nothing in `promote-demo` writes
`status = 'confirmed'` — an invariant test asserts that **only** Rumour Guard can.

There is also a measured reason the script exists rather than waiting for real
corroboration, and it is worth knowing before someone asks: recall is **~56%**. See
*Rough edges*.

## Verified without a device (2026-10-08)

- **The threshold was measured, not accepted.** `scripts/eval_dedup.py` over 18
  labelled duplicate pairs and 6 hard negatives in `data/eval/dedup/clusters.json`.
  **`DEMO_PLAN.md` §9's declared 0.82 merges 1 of 18 pairs** — the guard would have
  been a no-op that looked implemented. Set to **0.72**: 10 of 18 merged, **zero false
  merges**.
- **Promotion, end to end, against the real schema.** `promote-demo` on the live
  Mohakhali news flag → `status=confirmed`, `source_count=2`,
  `confirmed_at=2026-10-08T16:23:54Z`, `confidence=1.0`, sources
  `['channel24', 'demo_second_source']`, served through `GET /risk/flags` in the
  contract shape. `--reset` returned it to `unconfirmed`, `source_count=1`,
  `confirmed_at=null`, `confidence=0.6`.
- **Accumulation helps both ways.** The guard compares an incoming summary against
  *every* summary already on the flag. A third account of the Mohakhali fire scores
  **0.736** against the accumulated pair (merges) while a different fire near Mohakhali
  rail gate scores **0.595** against the same text (does not). Corroboration gets easier
  as it accumulates; false merging does not.
- 250 backend tests pass, 23 of them new in `tests/invariants/test_rumour_guard.py`.
  `mypy --strict` clean on 83 files.

## Fallbacks

- **No solid pins anywhere in view.** You are looking at an area with only
  single-source flags. Zoom out over central Dhaka — the fixture's confirmed flags are
  spread across it — or just do steps 7–9, which *create* one.
- **`promote-demo` says "no unconfirmed flag to promote".** Every served flag is
  already confirmed or already carries the demo source. `promote-demo --reset` puts one
  back.
- **The pin does not change shape after step 8.** Tap **↻** first; the map does not
  poll. If it still has not changed, the backend is on `RISK_SURFACE_IMPL=seeded` —
  the offline replay serves a fixture and `promote-demo` writes to the database.
- **`embeddings_available()` is `False`.** The model download failed. Steps 1–6 and
  7–11 still work (the scripted promotion does not embed anything); only automatic
  merging of real news is off, and it logs that it is off rather than failing quietly.

## Rough edges

- **Recall is ~56%, by choice.** True duplicates and genuinely different events in one
  neighbourhood are **not separable** on a one-line summary: the lowest true duplicate
  pair scores 0.503 and the highest false pair 0.718. There is no threshold that gets
  all of one and none of the other. 0.72 is the highest with zero false merges, so some
  real corroboration is missed — the flag stays unconfirmed and a duplicate pin
  remains. That is the cheap failure; a false `confirmed` badge is the expensive one.
  **Re-run `scripts/eval_dedup.py` after any change to `DEDUP_MODEL` or to what gets
  embedded** — the number is a property of the model and the text, not of the problem.
- **The margin is 0.002.** The worst false pair scores 0.718 and the threshold is 0.72.
  That is a coincidence, not a margin, and it is why `find_duplicate()` declines rather
  than guesses whenever the `kind`, distance or time gates are unsatisfied. Improving
  this needs a better signal — embedding the location alongside the summary, or a
  cross-encoder — not a different number.
- **Same-owner outlets still count as two sources.** `DEMO_PLAN.md` §D05 pre-declared
  this as the first cut, to Track B. `app/policy/independence.py :: _SAME_OWNER` is the
  seam: populate it and two outlets owned by one house stop corroborating each other,
  with no other change. It is empty because guessing Bangladeshi media ownership from
  memory would be worse than admitting the gap. **If a judge asks, this is the honest
  answer, and the map is the demo of what we do have.**
- **`confidence` is carried but not yet consumed by routing.** D06 must multiply by it
  (`app.scoring.decay.effective_severity`), or an unconfirmed flag will bend a route
  exactly as hard as a corroborated one and the tier will be decoration. There is a
  test pinning the ordering it is supposed to produce.
- **The eval clusters are hand-written** in the extraction model's style, not captured
  from real runs, because live ingestion has produced one flag so far. The format is
  identical to real `summary_en` values, so replacing them as the corpus grows is a
  straight swap and strictly better.
- **`demo_second_source` is visible in the flag sheet.** By design — a synthetic
  corroboration must be distinguishable from a real outlet without anyone having to
  remember that it is synthetic. Do not rename it to look like a publisher.
