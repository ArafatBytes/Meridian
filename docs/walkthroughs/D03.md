# D03 — Bangla search that actually works

**Ran on:** iPhone, Expo Go · **By:** Nakib · **Date:** 2026-10-08 · **Takes:** ~8 minutes

**Every step below passed on a real device.** One defect was found by running it and is fixed:
route mode had no reachable exit. See *Rough edges*.

## What this proves

Demo beat 3. You type **"Mirpur 10 golchattar"** — a Dhaka colloquialism in romanised Bangla — and
the map flies to the right roundabout and tells you *how* it knew. You type the same thing in Bangla
script and it works. You type a place that does not exist and it **says so** instead of guessing.

The interesting half is the refusal. A general-purpose map either finds something or finds nothing;
this one knows the difference between "we have never heard of this", "we know this name belongs to
two different places 10 km apart", and "a model thinks it knows". Those surface differently on
purpose.

Why "Mirpur 10 golchattar" is the test case and not a soft one: OpenStreetMap spells that roundabout
**গোলচক্কর** (*golchokkor*). Much of Dhaka says **গোলচত্বর** (*golchattar*). They are different words
for one place and share almost no letters, so no amount of fuzzy matching gets from one to the other.
It works because a person wrote the synonym down in `backend/data/gazetteer/aliases.json`. That file
is the thing Google cannot do for Dhaka, and it is worth saying out loud on stage.

## Preconditions

1. **`backend/.env` has at least one working key for this feature.** `GEMINI_KEY_GEO_ONE` is the
   primary. Keys and chains are named per feature, so a `GEMINI_KEY_*` without `GEO_` in it will
   not be found — that is deliberate, see `app/llm/client.py`. Check the shape
   without printing the value:

   ```powershell
   Select-String -Path backend\.env -Pattern '^(GEMINI_KEY_GEO|GROQ_KEY_GEO|LLM_CHAIN_GEO)' | ForEach-Object { ($_ -split '=')[0] }
   ```

   If `LLM_CHAIN_GEO` is absent the default in `app/core/config.py` applies, which is the measured one.

2. **The gazetteer files exist and are committed.**

   ```powershell
   Get-Item backend\data\gazetteer\dhaka_central.json, backend\data\gazetteer\aliases.json
   ```

   `dhaka_central.json` should be ~1,000 entries. If it is missing, rebuild it:

   ```powershell
   cd backend
   .\venv\Scripts\python.exe scripts\harvest_gazetteer.py
   ```

   That queries OpenStreetMap. The public Overpass mirrors are genuinely flaky — if one times out the
   script says so and retries the next, and answers are cached in
   `backend\data\gazetteer\.osm-cache\` so a re-run resumes rather than starting over. It is not a
   demo-time dependency: the JSON is committed.

3. **The backend is running — and the image must be rebuilt once for this sprint.**

   ```powershell
   .\scripts\run.ps1 -Rebuild
   ```

   **`-Rebuild` is mandatory the first time you start D03** and only the first time. D03 is the first
   sprint that adds a Python dependency (`openai`, in `requirements/agents.txt`), and the Dockerfile
   keeps requirements in their own cached layer so that code changes rebuild instantly. A plain
   `docker compose up -d` reuses that cached layer, so the container starts with D01's packages and
   dies at import with:

   ```
   File "/app/app/llm/client.py", line 78, in <module>
       import openai
   ModuleNotFoundError: No module named 'openai'
   ```

   The dependency is declared correctly; the image simply predates it. After this once, plain
   `.\scripts\run.ps1` is right again.

   **Use `run.ps1`, not a bare `docker compose` command.** It also sets
   `EXPO_PUBLIC_API_BASE_URL` to your LAN IP, which is what lets the *phone* reach the API —
   `frontend/src/constants/app.constants.ts` reads it, and there is a test on that file precisely
   because the URL was once hardcoded and "correct on exactly one network". Starting the containers by
   hand leaves the app pointing somewhere the phone cannot reach, and step 1 fails for a reason that
   has nothing to do with search.

   *(D02's walkthrough used `docker compose up -d --force-recreate api` because its step 15 edits
   `RISK_SURFACE_IMPL` in `backend\.env`, and compose reads `env_file` when a container is **created**
   — a plain `restart` keeps the old values. D03 changes no `.env` value during the run, so that flag
   is not needed here.)*

4. **Expo Go on the phone, same Wi-Fi as the laptop.** Same as D01 and D02.

## Steps

| # | Do this | Expect |
|---|---|---|
| 1 | Open the app, go to the **Map** tab. | The map, the D02 risk-flag pins, and a **new search box across the top**. Placeholder reads `Mirpur 10 golchattar`. |
| 2 | Tap the box and type **`Mirpur 10 golchattar`**. Press the search/return key. | A brief spinner, then the map **flies north-west to Mirpur 10** and zooms in tight. A dark-green pin appears. Below the box: **Mirpur-10 Circle** and a green chip reading **"From our Dhaka gazetteer"**. |
| 3 | Tap the ✕ to clear, then type **`মিরপুর ১০ গোলচত্বর`** (Bangla keyboard, or paste it). | **The same place, the same green chip.** This is the point: one gazetteer, either script. |
| 4 | Clear. Type **`Jatrabari chourasta`**. | Flies south-east to **Jatrabari Mor**. Green chip. (`chourasta` is the alias; OSM calls it `Mor`.) |
| 5 | Clear. Type **`Shahbagh mor`**. | **Shahbag Intersection**, green chip. Note the spelling — OSM has `Shahbag`, you typed `Shahbagh`. |
| 6 | Clear. Type **`Mirpur 10 Cirlce`** — the typo is deliberate. | Still resolves to **Mirpur-10 Circle**, green chip. The fuzzy tier handles transposed letters. |
| 7 | Clear. Type **`Hatirjheel`**. | Flies to Hatirjheel, but with a **blue pin** and a blue chip reading **"Inferred by AI"**. Hatirjheel is not in the gazetteer, so the LLM tier answered. Takes 1–3 seconds longer than steps 2–6. |
| 8 | Clear. Type **`Sector 11`**. | **No pin, no fly.** Below the box: *"Could not find "Sector 11". We will not guess a location."* This is correct — Dhaka has an Uttara Sector 11 and a Bashundhara Sector 11, about 10 km apart. |
| 9 | Clear. Type **`Sector 10`**. | **Resolves**, green chip. Contrast with step 8: the refusal is about ambiguity, not about sectors being unsupported. |
| 10 | Clear. Type **`Kolabagan Antarctic Research Station`**. | *"Could not find…"*. The LLM was asked and declined. |
| 11 | Clear. Type **`মিরপুর ৯৯ নম্বর গোলচত্বর`** (Mirpur sector 99 — there is no such thing). | *"Could not find…"*. |
| 12 | Clear. Type **`Eiffel Tower`**. | *"Could not find…"*. It is a real place and the model knows exactly where it is; the answer is discarded because it is outside the Dhaka box we claim to cover. |
| 13 | Tap the blue **navigate** button (upper right) to enter route mode. | The place-search box is **replaced** by the route source/destination card, headed **Plan a route** with a small **x** on its right. They do not stack or overlap, and the blue navigate button is hidden. |
| 14 | Tap that **x** in the card header. | Route mode closes. The place-search box and the navigate button return, and the pin from your last search is still on the map. |

## Steps 8 vs 10 — the distinction worth narrating

These look the same on screen and are different underneath, which is the most defensible thing in
this sprint:

- **Step 8, "Sector 11"** — our own gazetteer refuses, and **the LLM tier is not even asked.** The
  gazetteer knows something the model does not: that this name belongs to two records 10 km apart. A
  model asked this question answers Uttara's, confidently. Letting it do so would mean our ambiguity
  guard was overturnable by the weaker tier below it. It was, until the eval caught it.
- **Step 10, "Kolabagan Antarctic Research Station"** — the gazetteer has never heard of it, so the
  LLM *is* asked, and declines.

If a judge asks "so what stops the AI from making something up", step 8 is the better answer, because
the guard is ours rather than the model's good behaviour.

## Checking the backend directly

Useful if the phone misbehaves and you need to know which half is wrong.

```powershell
curl.exe -s -X POST http://localhost:8000/api/v1/geo/resolve `
  -H "Content-Type: application/json" `
  --data-binary '{\"text\":\"Mirpur 10 golchattar\"}'
```

Expect `"method":"gazetteer"`, `"confidence":1.0`, lat ≈ 23.8071, lon ≈ 90.3686.

Bangla over curl on PowerShell is awkward to quote — if you need it, use the app or write the JSON to
a file and pass `--data-binary "@body.json"` with the file saved as UTF-8.

## Rough edges

- **Fixed during the first device run: route mode had no exit.** The button that left
  route mode was positioned *inside* the route card, which carries a higher z-order,
  so it could not be tapped — and `toggleRouteMode` is the only exit, which made a
  reload the only escape. The close control now lives in the card's own header and
  the floating button only *enters* route mode. Worth knowing because it would have
  stranded the demo if anyone tapped navigate on stage. `tsc`, ESLint and Jest were
  green throughout; z-order and reachability are not things they can see.

- **`Mirpur 10` alone resolves to a bus-stand record, not the roundabout.** Both are named "Mirpur
  10" in OSM and they are ~150 m apart, so either answer is defensible and the tie-break picks the
  shorter name. Harmless at this zoom; worth knowing before someone reports it as a bug.
- **`Sayedabad bus terminal` resolves to the Saydabad *area*** (1.2 km radius), not the terminal
  building. The area circle covers the terminal. Good enough for the demo; a hand-added alias would
  sharpen it.
- **The LLM tier takes 1–3 s**, occasionally longer. Steps 2–6 are instant because they never leave
  the gazetteer. If a judge is watching, lead with the gazetteer cases.
- **Free-tier quota.** `gemini-3.5-flash-lite` allows 500 requests/day on this account and the
  fallback `openai/gpt-oss-120b` 1,000/day on a different provider. Rehearsing steps 7 and 10–12
  thirty times will not exhaust it, but the quota resets at midnight Pacific, so do not do a 400-query
  sweep on the 23rd.
- **ODbL.** The gazetteer is OpenStreetMap data. Attribution lives in the `_README` block of
  `dhaka_central.json` and an invariant test fails if it is removed. If the gazetteer is ever
  published as a dataset, it must go out under ODbL too.

## Fallback if it fails live

| Fails | Do this |
|---|---|
| LLM key dead, quota gone, or no network | **Nothing.** Steps 2–6 and 8–9 are pure gazetteer — no network beyond the local API. Only step 7 needs the model. Resolution accuracy with the LLM tier entirely disabled is **93.3%**, measured. Say that number. |
| The search box resolves nothing at all | The gazetteer file is missing or unreadable in the container. `docker compose exec api ls -la data/gazetteer/`. Rebuild per precondition 2. |
| Bangla renders as boxes on the device | A font problem, not a search problem. Demo the romanised cases and say so. |
| A place a judge types is missing | Correct behaviour, and say so plainly: one pilot zone, 150-landmark target, national coverage is Track B (B7). Then type a case from steps 2–6. **Do not** widen a threshold to make an unknown place resolve. |

## Numbers

Measured on 2026-10-07 by `backend/scripts/eval_geocoding.py` against the 53-case held-out set in
`backend/data/eval/geocoding/references.json`. Re-runnable; baselines in `baseline.json`.

| | Gazetteer only | Gazetteer + LLM |
|---|---|---|
| Accuracy on real places | **93.3%** | **100%** |
| Correct refusals on fakes | **100%** | **100%** |
| **Fabrications** | **0** | **0** |
| Median error (hits) | 6 m | 6 m |
| Worst error (hits) | 581 m | 581 m |
| Network needed | none | one request per gazetteer miss |

**"Fabrications" is the number to quote**, not accuracy. It counts coordinates returned for a place
that does not exist — the failure that puts somebody on a road on a claim nobody made. Zero, both
ways.

### The gazetteer

| | |
|---|---|
| Entries | **1,022**, harvested from OpenStreetMap |
| Hand-reviewed, with aliases | **22** entries carrying **100** aliases |
| Named junctions (মোড় / চৌরাস্তা / চত্বর) | 55 |
| Flagged ambiguous and refused on purpose | 123 |

D03 asked for 150+ entries; the harvest gives 1,022. The honest caveat is that **22 are reviewed**,
not 1,022 — the rest resolve on their own OSM names, which is why `reviewed` is a field and not an
assumption. Extending that is B7.

### Model selection

**First pass — a six-case probe**, two independent runs, 2026-10-07:

| Model | Score | Note |
|---|---|---|
| `gemini-3.5-flash-lite` | **6/6** | chosen primary. Refused both fabricated places |
| `gemini-3.1-flash-lite` | 5/6 | **rejected** — invented coordinates for a nonexistent Mirpur sector, reproducibly, at 0.95 confidence |
| `openai/gpt-oss-120b` | 4/6 | refusals correct; put Sayedabad 12.6 km off |
| `qwen/qwen3.8-27b` | 1/6 | disqualified — both refused real places and fabricated a fake one |

**Second pass — the full 53-case set, because six cases was too thin to decide on.**
`gpt-oss-120b` was run alone, both bypassing the gazetteer (which measures the
model) and as the system's only model (which measures what would happen if Gemini
were unavailable). Gemini was not re-run model-only, by the owner's instruction, so
its column is the shipped `with_llm` baseline.

| | `gemini-3.5-flash-lite` | `openai/gpt-oss-120b` |
|---|---|---|
| Model alone, gazetteer bypassed | not measured | **15.6%** accuracy, **2 fabrications**, 25 wrong answers |
| As the system's only model | **100%** accuracy, **0 fabrications** | 95.6% accuracy, **1 fabrication** |

**The six-case probe flattered `gpt-oss-120b` badly.** 4/6 became **15.6%** over 45
real places — 25 of them resolved confidently to the wrong location. Its refusals
also stopped holding up: it invented coordinates for **"Gulshan 97 golchattar"**, a
circle number that does not exist, and for **"মিরপুর ৯৯"** and **"Sector 11"** once
the gazetteer was out of the way.

The 95.6% column is almost entirely the gazetteer's work — 42 of 53 cases never
reach a model at all. `gpt-oss-120b` handles four, and on those four it produced one
fabrication plus Hatirjheel 1.68 km out and Bashundhara City 3.94 km out.

**So the fallback is a liability, not insurance** — see *Open decision* below.

**A robustness bug this measurement exposed.** `gpt-oss-120b` returns
`json_validate_failed` with empty output on roughly 1 in 10 calls, and the client
used to **raise** on it, because a 400 is normally our own fault. With Gemini rate
limited and a request falling through to Groq, a map search would have returned HTTP
500 instead of an honest "could not find that place". Model-side 400s now fall
through to the next option; genuinely bad requests from us still surface. Two
invariant tests pin both halves.

### Open decision — should the `GEO` fallback exist at all?

`LLM_CHAIN_GEO` still ends in `groq:openai/gpt-oss-120b`, which **has not been
changed pending a decision**, because both options cost something real:

| | If Gemini is unavailable |
|---|---|
| **Keep the fallback** | 95.6% accuracy, but **1 fabrication** — the discard invariant holds only while Gemini is up |
| **Drop it** | gazetteer only: **93.3%** accuracy, **0 fabrications**, no network needed. Loses the handful of places not in the gazetteer (Hatirjheel, Road 27 Dhanmondi, Bashundhara City) |

**Recommendation: drop it.** 2.3 points of accuracy is not worth a fabrication when
*"a wrong pin is worse than no pin"* is the stated invariant and the thing a judge is
most likely to test. Dropping it also means the degraded path needs no network at
all, which is the venue-failure story. Adding a second *Gemini* model would not help:
same provider, same rate limit, and `gemini-3.1-flash-lite` fabricates too.
