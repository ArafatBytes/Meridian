# D04 — Today's news, on the map

**Ran on:** Expo Go · **By:** Arafat · **Date:** 2026-10-08 · **Takes:** ~10 minutes, plus the
offline pass

**Every step below passed on a real device, live and offline.** Running it found **three** defects
that the backend verification could not — two of them not in D04's code at all. All three are fixed;
see *Found by running this*.

## What this proves

Demo beat 1 and half of beat 2. The map is not a static fixture: an agent reads **today's Bangla
news** from three outlets, finds the events that affect movement in Dhaka, locates them in the
gazetteer, and puts them on the map as **unconfirmed** flags. Tap one and you see **the real headline,
the outlet and how long ago it was published** — and you can open the article itself.

Then the network goes away and the same news flags are still there, replayed from a capture. The
venue's wifi cannot decide whether beat 1 works.

What a judge should notice: every news flag says **Unconfirmed · 1 source**. One outlet is one
source, and one source never confirms anything — that is D05's job and the database refuses
otherwise.

## Preconditions

1. **Rebuild the image once for this sprint.** D04 adds Chromium for Playwright (Channel 24 renders
   its articles with JavaScript) and a new container, `worker`.

   ```powershell
   .\scripts\run.ps1 -Rebuild
   ```

   `run.ps1`'s `docker compose up -d` starts the new `worker` with everything else. `docker ps`
   should list `meridian-api`, `meridian-worker` and `meridian-redis`.

2. **`backend/.env` has the EXTRACT key**, from a different Google project than the GEO key (Gemini's
   free quota is per project). Check the names without printing values:

   ```powershell
   Select-String -Path backend\.env -Pattern '^(GEMINI_KEY_EXTRACT|LLM_CHAIN_EXTRACT)' | ForEach-Object { ($_ -split '=')[0] }
   ```

   `GEMINI_KEY_EXTRACT_ONE` must be listed. `LLM_CHAIN_EXTRACT` may be absent; the default applies.

3. **The D04 migration is applied** (`20261008120000__raw_documents_extracted_at`):

   ```powershell
   docker exec -w /app meridian-api python scripts/migrate.py status
   ```

   All three must show `applied`. On a database that has not had it yet,
   `docker exec -w /app meridian-api python scripts/migrate.py up` applies it. *(Before D04, `status`
   reported `20261007120100` as CHANGED and `up` refused to run. That was line endings, not an edit —
   fixed in `migrate.py`; see `PROGRESS.md`.)*

4. **There are live news flags to look at.** The worker reads the news every 15 minutes on its own.
   **Run the walkthrough in Dhaka daytime** — at 4 a.m. the outlets publish almost nothing about
   Dhaka's roads, and an empty result is correct, not broken. Check what the last runs found:

   ```powershell
   docker exec -w /app meridian-api python -m app.agents run live_risk --dry-run
   ```

   The JSON at the end shows `relevant`, `documents_read`, `incidents` and `published`. A dry run
   writes nothing, so it is safe to repeat.

5. **Signed in on the phone** (the "fetch news now" button needs a session), Expo Go current, same
   Wi-Fi as the laptop.

### Finding the news flag

Step 6 originally said news flags *"look like any other flag; tap pins until the sheet's Source line
names an outlet."* With 212 fixture flags on the map that is not a procedure — it is a search. Three
things make it worse, and all three are by design:

- **Pin colour encodes decayed severity, not provenance.** `RISK_SEVERITY_BANDS` is red ≥ 70,
  orange ≥ 50, yellow ≥ 30, blue-grey below. A news flag is whatever colour its current severity
  says, and most fixture flags are blue-grey, so a *fresh* news flag stands out only while it is young.
- **Crime-report markers are a second, unrelated colour scheme** (`CRIME_COLORS`: purple =
  harassment, orange = theft, pink = assault …). They are D01's work and have nothing to do with
  D04. Note that theft `#FF9800` and High-severity `#F57C00` are both orange — you cannot tell a
  crime report from a risk flag by colour.
- **Fixture flags are `unconfirmed` too**, so "tap the unconfirmed ones" does not narrow it either.
  D05 made that state visible — a news flag is a **hollow, dashed marker with a `?`** — which rules
  out every *confirmed* flag at a glance but not the ~39 unconfirmed fixture ones. Narrowing, not
  solving; the coordinate lookup below is still the reliable route.

Ask the backend instead, then go to the coordinates:

```powershell
curl.exe -s "http://localhost:8000/api/v1/risk/flags?bbox=90.30,23.70,90.50,23.85" | `
  python -c "import sys,json; [print(f['lat'], f['lon'], f['severity_now'], f['sources'][0]['source_id']) for f in json.load(sys.stdin) if not f['sources'][0]['source_id'].startswith(('sample','bd_'))]"
```

**In PowerShell use `curl.exe`, not `curl`** — bare `curl` is an alias for `Invoke-WebRequest`,
which throws a .NET exception instead of printing a body.

Then zoom hard into those coordinates. **Do not use the D03 search box to get there:** a news flag
resolved through the gazetteer sits at *exactly* the gazetteer entry's coordinates, and the search
marker renders after the risk pins, so it covers the pin you are looking for.

## Steps — offline (the D04 gate's second pass)

The offline demo has no database, no model and no publisher. It serves the **replay**: a capture of
real news flags in fixture form, re-anchored to the moment the backend starts.

| # | Do this | You should see |
|---|---|---|
| O1 | **Capture** while live flags exist (step 6 found at least one): `docker exec -w /app meridian-api python -m app.agents export-replay` | `exported N live flag(s) to the replay fixture`. The file is `backend/data/fixtures/live_replay.json`. **Commit it** — it is the offline demo's beat 1. |
| O2 | In `backend\.env` set `RISK_SURFACE_IMPL=seeded`, comment out `GEMINI_KEY_EXTRACT_ONE`, and break `DATABASE_URL` by **editing only the hostname** — keep the scheme, user, password, port and database name, and change the host between `@` and `:5432` to `nowhere.invalid`. ⚠️ **The value must still parse as a URL.** `create_async_engine` runs at *import* time in `app/core/database.py`, so an unparseable `DATABASE_URL` kills the process before FastAPI exists and `/health` answers nothing at all. A host that does not resolve is what you want; a placeholder string is not. The original line is recoverable with `git show HEAD:backend/.env \| Select-String '^DATABASE_URL='`. | — |
| O3 | `docker compose up -d --force-recreate api` (not `restart` — compose reads `.env` at create time). | `(Invoke-WebRequest http://localhost:8000/health).StatusCode` → **200**, and `docker compose logs --tail 20 api` contains **`⚠️ Database not available`**. That warning is the success signal, not a problem: `lifespan()` wraps `init_db()` in try/except and carries on, which is the whole claim this pass exists to prove. |
| O4 | Reload the app (shake → Reload). | The pill reads `● N risk flags · offline replay`, and **the newspaper icon is gone** — there is nothing to fetch into. |
| O5 | Tap a news flag from the capture. | The same outlet, headline and link as live, and `Unconfirmed · 1 source`. **Its age is preserved, not reset** — see *The replay keeps the flag's age* below. |
| O6 | Undo O2 and `docker compose up -d --force-recreate api`. | Back to live. |

*Breaking the database URL and the key proves the replay depends on neither. For a stricter rehearsal,
unplug the router's internet uplink while keeping the Wi-Fi up, so the phone still reaches the laptop.
Note that `--force-recreate api` does **not** touch `meridian-worker`, which keeps its old environment
and carries on ingesting — `docker compose stop worker` first if you want the uplink test to be honest.*

### The replay keeps the flag's age

`export-replay` stores **relative** times (`observed_offset_hours`), which is right: absolute
timestamps would be expired by the morning of the 24th. But "re-anchored to the moment the backend
starts" preserves the *offset*, it does not zero it. The offset is `article publish time − export
time`, so **the flag replays at whatever age it had when you captured it, forever.**

The capture taken on 2026-10-08 reads:

```
observed_offset_hours  -4.1          → always 4.1 hours old
severity_0 70, half-life 3.5 h       → always severity 31.1  → 🟡 yellow, 1.1 above the blue-grey band
```

That is honest and it works, but it is a weak beat 1: one barely-yellow pin among 48 blue-grey
fixtures. **Capture earlier in a flag's life for a stronger demo** — the same flag exported at 12:19
instead of 13:36 would have been −2.8 h and severity 40. You cannot improve an existing capture;
waiting only makes the offset worse. Re-run `export-replay` whenever a fresher news flag exists — it
captures every live flag, so a newer one simply joins the file.

⚠️ **Do not hand-edit `observed_offset_hours` to fake freshness.** The fixture's own README says not
to, and a judge who taps the headline sees the article's real publication time. That trade is not
worth it.

## Fallbacks

- **No news flags in step 6.** Nothing in today's news located inside the pilot zone, or it is early
  morning. Say so — "we refuse to guess a location, so quiet news means a quiet map" — and switch to the
  offline replay (O2–O4), which carries a captured run.
- **The newspaper icon runs for ~20 s and nothing changes.** Expected, and the common case. The
  relevance filter picks the same handful of articles every run, and once they are in
  `raw_documents` they are skipped on URL — so a tap reports `fetched: 0, documents_read: 0,
  published: 0` and spends no quota. Measured across eight consecutive runs on 2026-10-08:
  `listed` climbed 480 → 494 while `relevant` stayed pinned at **3**, all already consumed. Step 4
  says "**if** the outlets published something since the last run" and that conditional is doing more
  work than it looks. **For the stage, decide in advance** whether to narrate it honestly ("it just
  checked 494 articles across three outlets; the three about road incidents are already on the map")
  or to clear `extracted_at` on one document beforehand so the tap produces a visible pin.
- **`reading news…` never finishes.** The app gives up after 3 minutes. Check the worker or API log:
  `docker compose logs --tail 50 api`. A Gemini 429 shows as `LLMUnavailable` in the run's errors;
  documents stay queued and the next run reads them.
- **Tap on the newspaper does nothing.** Not signed in (the endpoint answers 401), or the backend is on
  `RISK_SURFACE_IMPL=seeded`, where the button is hidden.

## Found by running this

Three defects. **Two were not in D04's code**, which is the argument for the §0 device gate: a green
backend, `tsc`, ESLint and 193 passing tests had all three.

1. **The gazetteer discarded the one real news event of the day** — and therefore live ingestion had
   **never published a flag**, through every run since the agent was built. A genuine Mohakhali bus
   fire was extracted at **0.95 confidence** and dropped as `unresolved_location`, because the model
   was asked for "the most specific place name", answered `মহাখালী বাস টার্মিনালে`, and the
   gazetteer resolves `মহাখালী` at 1.00 and that phrase at nothing. **The most specific answer was
   the least resolvable one.** `PLACE_FILLER` did not help: `বাস` and `টার্মিনালে` are part of the
   name, not wrapping around it.

   Fixed with `PLACE_GENERIC_TAIL` in `app/agents/live_risk.py` — generic place-*type* nouns stripped
   from the **end only**, longest match first, because Bangla puts the specific name first. Candidate
   order is as-written → filler-stripped → tail-stripped, so a place the gazetteer knows in full
   (`যাত্রাবাড়ী চৌরাস্তা`, `কারওয়ান বাজারে`) still resolves to **itself**, never to its prefix.

   **The discard invariant is intact**, and that was the hard part. A naive prefix fallback was tried
   first and rejected: it resolved the fabricated `গুলশান ফ৭ গোলচত্বর` to Gulshan. What saves the
   chosen fix is **D03's number-identity rule** — that phrase reduces to `গুলশান ফ৭`, which matches
   nothing, so it is still refused. Three regression tests in
   `tests/invariants/test_live_flags_are_unconfirmed.py` pin all of it, including "a known place
   resolves to itself not its prefix" and the ambiguity refusal for `উত্তরা সেক্টর ১১`.

2. **Every authenticated backend call 401'd about an hour after sign-in** — which is why the
   newspaper icon failed with `No refresh token`. Not a D04 defect; D04 is just the first feature
   that needed a token on a session older than an hour.

   `api.service.ts` read the access token from a `SecureStore` copy written once at sign-in and
   never refreshed, and Supabase access tokens last one hour. The 401 recovery path then POSTed to
   the backend's `/auth/refresh`, which is a `# TODO: Implement token refresh logic` stub that takes
   `refresh_token` as a query parameter while the app sent a JSON body — so it would have failed even
   if it were implemented. Meanwhile the Supabase client, created with `autoRefreshToken: true`, held
   a **valid** token in AsyncStorage the entire time.

   Fixed by making `supabase.auth.getSession()` the only source: in `auth.service.getAuthToken()`,
   in the axios request interceptor, and in the 401 handler (now `supabase.auth.refreshSession()`).

   ⚠️ **`HomeScreen` SOS was broken the same way and nobody had noticed**, because `D01.md` is
   normally run just after signing in. It read `useAuthStore().token`, captured once by
   `initialize()` and never updated, so an SOS from an older session uploaded the video and *then*
   got a 401. It now fetches the token at trigger time. **This is beat 9, and it was silently dead.**
   Exactly the cross-sprint breakage `DEMO_PLAN.md` §8 row 3 predicts.

3. **O2 as written bricked the API.** `DATABASE_URL=...@nowhere.invalid:5432/...` was meant as
   "change the host", read as copy-paste, and an unparseable URL raises in
   `create_async_engine` at import — before FastAPI exists, so `/health` returns nothing rather than
   200. O2 and O3 above now say what to preserve and give `⚠️ Database not available` as the signal
   to look for.

  filter, all 4 fetched (Channel 24's through Playwright, full body), read by Gemini, recorded in
  `raw_documents` and `agent_runs`. None reported a Dhaka road event at 04:25 Dhaka time, which was the

- The publish path against the real schema, inside a rolled-back transaction: a news-phrased place
  (`রাজধানীর মিরপুর ১০ নম্বর গোলচত্বর এলাকায়`) resolved to Mirpur-10 Circle, the flag was inserted

  `Road blocked near Mirpur-10 Circle.`; a fabricated place (`গুলশান ৯৭ গোলচত্বর`) was recorded as
  `unresolved_location` and produced no flag.

## Rough edges

- **The gazetteer covers central Dhaka only.** News about Uttara's far sectors, Savar or Narayanganj is
  extracted and then discarded as `unresolved_location`. The audit trail is in `extracted_incidents`.
- **Headlines are shown as published.** They are the outlet's words, quoted as provenance, and may
  contain vocabulary the framing guard would refuse in a flag statement (e.g. সংঘর্ষ). The product's
  own claim is only ever the framed line at the top of the sheet.
- **`DEBUG=true` makes the API and worker logs very loud** — SQLAlchemy echoes every statement,
  including article bodies. Use `grep app.agents` on the logs.
