# ADR 0002 — Supabase is the identity provider; the backend only verifies

---

## Context

There is exactly one place a Meridian user's identity can come from, and it is
Supabase Auth. The client signs in with the Supabase SDK, receives an access
token, and sends it to FastAPI as a bearer token. The backend's job is to decide
whether that token is genuine.

That decision has a history worth recording, because it is why this ADR was
written late.

**Defect 33.** `security.py` called
`jwt.decode(token, JWT_SECRET_KEY, algorithms=["HS256"])` and **every
authenticated request failed** with *"The specified alg value is not allowed"*.
Supabase now signs access tokens with asymmetric keys by default: the tokens
carry `{"alg": "ES256", "kid": ...}` and the project publishes the matching
public key at `{SUPABASE_URL}/auth/v1/.well-known/jwks.json`. No value of
`JWT_SECRET_KEY` could have fixed it — HS256 is a symmetric MAC and the token is
an ECDSA signature. The secret was never the problem. `app/core/jwks.py` now
fetches the JWKS, caches it for 600 s, and refetches on an unknown `kid`.

Verifying against a published public key is also better than the shared secret
it replaced, for a reason that is the heart of this ADR: **the backend ends up
holding a credential that can only check tokens, never mint them.** A leaked
JWKS cache is worthless to an attacker, and Supabase can rotate signing keys
without a coordinated backend deploy.

## Decision

**1. Supabase Auth is the only identity provider. The backend verifies tokens
and never issues them.**

No password reaches FastAPI. No session is created by FastAPI. There is no local
user table to authenticate against — ADR 0003 removed the last one. Registration,
login, logout, password reset and token refresh are all client-to-Supabase.

**2. `auth.users(id)` is the identity, and `public.profiles` is the display
layer.** Every `user_id` column in the schema references `auth.users(id)`
(SCHEMA.sql lines 84, 126, 155, 205, 234). `profiles` holds name, phone and
avatar and is written Supabase-direct under RLS by its owner. A backend that
needs a human-readable name reads `profiles.name` — see
`endpoints/sos.py::_display_name`, and defect 9 for what happens when it does
not.

**3. Verification requires a `kid` the project publishes.** HS256 is accepted
only as a fallback for a legacy shared-secret project, and — see below — that
fallback is the one part of this design that has been actively harmful.

## ⚠️ Finding, 2026-10-15: the decision above was not actually enforced

Writing this document meant reading the auth path end to end for the first time
since defect 33, and it does not do what decision 1 says.

**`POST /api/v1/auth/login` mints a valid token for any email, with no
credential check at all.** It is registered in `app/api/v1/api.py`, it is
unauthenticated, and its body is:

```python
access_token = create_access_token({"sub": "user_id", "email": request.email})
```

`verify_password` is imported and never called. `/auth/register` is identical.
Both were left behind by the inherited application, under a
`# TODO: Implement login logic` comment, and ADR 0001 shows the client has
routed around all of them — `api.service.ts` refreshes through
`supabase.auth.refreshSession()` and documents in a comment that
`/auth/refresh` is a stub.

**Measured, not inferred.** Minting a token through `create_access_token` and
passing it to the real verifier:

```
JWT_SECRET_KEY set? True | len 88      JWT_ALGORITHM: HS256
verify_supabase_token(...)  -> *** ACCEPTED ***
get_current_user(...)       -> {'user_id': 'user_id', 'email': 'attacker@example.com'}
```

So the full chain holds: an unauthenticated endpoint hands out a token, the
verifier accepts it, and `get_current_user` returns a principal. **Every FastAPI
endpoint behind that dependency is reachable without credentials** — including
`/sos/trigger`, which now emails a police station, and `/ai/*` and `/casework/*`,
which spend LLM budget.

Three distinct faults, and each is sufficient on its own:

1. **The backend can mint tokens.** `create_access_token` /
   `create_refresh_token` exist and sign with `JWT_SECRET_KEY`, which
   contradicts the whole argument for JWKS. Their only caller is the dead
   `auth.py`.
2. **HS256 is accepted whenever `JWT_SECRET_KEY` is set**, so a minted token
   verifies. This project's real tokens are ES256; the fallback protects nothing
   here and is what makes fault 1 exploitable. Note that `.env` is committed
   deliberately (private repo), so this secret is not a secret in the usual
   sense.
3. **The audience check does not reject a token with no `aud` claim.** The
   verifier passes `options={"verify_aud": True}` and
   `audience="authenticated"`, and a forged token carrying no `aud` at all was
   still accepted. Requiring the claim to be *present* would have blocked this
   bypass by itself, and would reject nothing legitimate: a genuine Supabase
   access token always carries `aud: "authenticated"`.

### ✅ Fixed the same day, all three faults

Not the cheapest one. Each was independently sufficient, so each was removed.

| fault | fix |
|---|---|
| the minting endpoint | `endpoints/auth.py` deleted, with its `include_router` line and `schemas/auth.py` |
| the backend could sign | `create_access_token`, `create_refresh_token`, `verify_password`, `get_password_hash` deleted from `core/security.py` |
| HS256 accepted | `_ALLOWED_ALGORITHMS = {"ES256", "RS256"}`; a symmetric token is refused on the algorithm alone, before any key lookup |
| `aud` not required | `options["require"] = ["exp", "aud", "sub"]` — `verify_aud: True` alone did not reject a token without the claim |

**Verified, the same way the fault was found.** The forged HS256 token is now
`REFUSED: JWTError - Unsupported token algorithm: HS256`, and
`create_access_token` raises `ImportError`. Legitimate authentication is
unaffected: `/sos/history`, `/notifications/config` and `/users/me` all return
**401** for both a missing and a malformed token, and the API boots clean.

`tests/invariants/test_the_backend_cannot_mint_a_token.py` (10 tests) is what
stops it returning. It asserts structure rather than behaviour, because the
bypass survived by **never being exercised** — the same reason defect 31's
unconditional police routing went unnoticed. So: no module under `app/` may call
`jwt.encode` at all; the four helpers must not exist by name; no `/auth` route
may be registered; `endpoints/auth.py` and `schemas/auth.py` must stay deleted;
a symmetric and an `alg: none` token must both raise; and the required-claims
list must still be there.

One of those tests reads `JWT_SECRET_KEY`'s readers **via `ast` rather than a
text scan**, because the first version flagged `core/security.py` — whose
docstring *explains* that the deleted helpers used to sign with it. Prose about
a credential is not use of it, and a check that cannot tell the difference gets
suppressed instead of fixed.

### `JWT_SECRET_KEY` is no longer an auth secret, and its name lies

Its only remaining reader is `app/agents/report_corroboration.py`, which uses it
as the HMAC key behind `reporter_ref` — B13's reporter pseudonyms. Two
consequences, recorded in `config.py` beside the setting:

* **Rotating it silently re-pseudonymises every reporter.** Old `reporter_ref`
  values stop matching new ones, so one person who reported twice becomes two
  people and corroboration counts change. It behaves like a schema constant, not
  a credential.
* The name invites the next reader to treat it as an auth secret and reintroduce
  symmetric verification. A rename belongs with a migration that touches
  `community_clusters`, not on its own.

`JWT_ALGORITHM` (which defaulted to `"HS256"` — the algorithm that signed the
forgeries), `ACCESS_TOKEN_EXPIRE_MINUTES` and `REFRESH_TOKEN_EXPIRE_DAYS` were
deleted. They described a backend that issues sessions.

## Consequences

**The client owns the whole sign-in journey.** Any future requirement here —
OAuth providers, magic links, MFA — is a Supabase configuration change plus
client work, with no backend deploy. That is the main practical benefit of this
decision and the reason not to reverse it for convenience.

**RLS can be trusted, which is what ADR 0001 is built on.** `auth.uid()` is
meaningful only because the token is Supabase's own. If FastAPI minted tokens
too, there would be two issuers and only one of them would be known to RLS.

**`bcrypt` and `passlib` stay in `requirements/base.txt` only as long as the
password helpers do.** They are listed under `# ---- auth ----` and, once the
helpers go, nothing imports them.

**Rate limiting and lockout are Supabase's.** This project has no login
endpoint to protect, which is a real benefit of not being an IdP and is worth
saying out loud when someone asks how brute force is handled.

**Service-role access remains the backend's own risk.** Verification is about
the *caller's* identity; the backend's own connection is a service-role
credential that RLS does not constrain. That is why ADR 0001 keeps agent output
and cross-user derivation on the FastAPI plane and nothing else.
